# PDCA 闭环与防偷懒规则详解

本文件解释为什么会有那些铁律，以及遇到具体失败模式时怎么处理。SKILL.md 是行动纲要，本文件是判例手册。

## 为什么 AI 会"偷懒"——根因

1. **完成的定义模糊**："整理一下""弄好它"没有可判定的终点，模型自然停在"差不多的概括"。
2. **自检是自说自话**：让同一次生成去评价自己，它倾向于认同自己。
3. **补全被当作新任务**：被指出小问题时，模型只针对那句话局部回应，丢失了"全集"这个上下文。
4. **证据成本被规避**：逐项举证比一句"弄好了"贵得多，没有强制机制就会被省略。

对策分别对应：清单基线、机械门禁、全量回归、强制证据。

## Check 阶段：如何做真自检

- **以机器结果为准**：跑门禁脚本，不用"我检查过了"代替。脚本会忽略自报 status。
- **反向验证**：对每个"完成"项问一句"如果它其实没做，我拿什么证明它做了？"——如果答不出证据，就是没做完。
- **全集视角**：自检永远从清单第一行开始逐项过，不从"上次出错的那行"开始。
- **数量核对**：页数、文件数、表格数、记录数这类可数指标，必须给出确切数字并与 universe 比对。

## Act 阶段：如何做真修复

- **先分流再动手**：
  - **系统性缺陷**——同类会复发（如乱码、字段丢失、格式错乱）：发现一处，用脚本在全部产物里扫描同类，统一修复。
  - **偶发单点**——一次性环境问题（缺字体、路径不存在、权限不够、单次网络失败）：就地修复并注明原因，不做全量扩散，避免无效重跑。
  - 判断标准：问一句"这个错误的成因会不会在其他单元重现"，会→系统性，不会→偶发。
- **根因修复**：如果错误来自某个处理步骤（如 OCR 参数），修步骤后重跑全集，而不是手工补结果。
- **全量回归**：改完后 `round + 1`，重跑整份清单。禁止"只验刚改的项"。
- **停滞即停**：某项连续两轮无进展，判为阻塞，写明卡点、缺什么、要谁给，转入阻塞态如实报告，不为凑 5 轮空转。

## 常见失败模式与对策

| 失败模式 | 典型话术 | 对策 |
|----------|----------|------|
| 概括式完成 | "主要内容已整理" | coverage 验证器要求逐项标识，概括无法产出 47 行证据 |
| 抽样代替全量 | "看了前几页，其余类似" | universe.total 固定，coverage 必须达到该数字 |
| 留小尾巴 | "还有几个小问题，不影响" | 禁止模糊话术；小问题必须枚举成清单项并逐个过门禁 |
| 虚报通过 | "全部完成了"（实际缺文件） | 门禁忽略自报 status，实际验证抓虚报 |
| 局部修复 | 改完一处就说好了 | 同类全量扫描 + 全量回归两条铁律 |
| 无限返工 | 每轮都冒出新问题 | 迭代上限 5 轮，到限如实报告卡点，不谎称完成 |
| 无证据交付 | "我确认过了" | 每个 pass 项必须非空 evidence，否则判失败 |

## 迭代上限的处理

第 5 轮仍未全绿，或某项连续两轮无进展（判阻塞）时：

1. 停止循环，不再声称完成，转入"阻塞"态。
2. 在自检报告中如实写明：卡在哪几个 item id、根因是什么、缺什么资源或权限、要谁提供。
3. 向用户请求明确输入（如：提供"仓颉 Skill"的具体调用方式、Obsidian 库路径、模板文件）。
4. 得到输入后，从 P0 重建清单重新开始，而不是从半途继续。

诚实报告比虚假完成更有价值——它让用户能真正接管。
