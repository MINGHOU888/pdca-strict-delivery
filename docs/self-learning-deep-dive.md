# 双环自学习怎么实现的

> 一份写给使用者的技术说明：这个 skill 的"越用越聪明"到底怎么运转、为什么不会退化成经验垃圾、每一环靠什么代码保证。
>
> 全文可独立阅读，不依赖仓库其他文件。命令示例均可在 `scripts/playbook.py` 上直接跑。

---

## 为什么大多数 Agent 不会自学习

先说清楚问题，不然后面看不懂设计。

一个 AI Agent 每次开工都是"从零开始"：它读了规则、列了清单、跑完门禁、交出成果——然后关窗。第二天开新任务，同样的坑它会再踩一遍。

原因不是模型笨，是**缺一个能跨任务持久化的载体**。对话上下文关掉就没了；就算在同一个会话里，"上次踩坑"也只是它上下文里的一段文字，不会自动变成"下次开工前的检查项"。

更隐蔽的是：**大多数 Agent 甚至不会主动承认自己踩过坑**。让它复盘，它会说"本次交付顺利"；让它总结教训，它会编三条听起来很深刻的原则。这些原则既没有根因、也没有验证方式，下一次用不上。

所以一个能用的自学习机制，必须解决三个问题：

1. **载体在哪** —— 教训得落到一个跨会话、跨任务还能读到的文件里，不能只活在对话里。
2. **怎么用上** —— 教训不能只是"存着"，得在**下一次开工之前**就变成清单里的检查项，否则等于没存。
3. **怎么不烂掉** —— 经验库跑久了必然重复、过时、被证伪。没有治理机制的项目，半年后就是一堆没人敢看的垃圾。

这个 skill 的双环结构就是逐条对应这三个问题。

## 双环结构

```
内环（单次任务）：P 计划 → D 执行 → C 自检 → A 复盘 → 交付
                                    ↓
                              发现可复用的坑
                                    ↓
外环（跨任务）：  经验库（qa/playbook.json）
                                    ↓
下次任务的 P 阶段：读经验库 → 变成预防项（EXP-xx）→ 清单里加检查项
```

**内环保证这一次做对**，**外环保证下一次做得更快**。

只有内环 = 每次都重新犯错。
只有外环没内环 = 存了一堆教训但当下照样错。
两个环都在 = 教训在**源头**被挡住，而不是做完再返工。

### 内环

内环是标准的 PDCA，只是每个环节都被改造成了"可判定"的动作：

| 环节 | 干什么 | 关键约束 |
|------|--------|---------|
| **P 计划** | 九维分解定全集 + 建验收清单 | 清单先落盘再动手；**P 阶段先读经验库** |
| **D 执行** | 按清单逐项做全集 | 批量活儿用脚本遍历，"全量"由代码保证 |
| **C 自检** | 跑门禁，脚本实跑取证 | 自报 status 被忽略，覆盖数从产物反推 |
| **A 复盘** | 缺陷修完 → 提炼可复用经验入库 | 根因必须附可复现的触发证据 |

内环里跟自学习直接相关的两处：

- **P 阶段加载经验**：`playbook.py list qa/playbook.json --when <本任务标签>`，把适用经验转成 `EXP-xx` 预防项加进清单。
- **A 阶段沉淀经验**：缺陷修好后，如果它具有可复用性（不是一次性笔误），立刻 `playbook.py add` 入库。

## 外环

外环是重点。它不是"把 AI 说的话存下来"，而是一条**有状态机、有证据要求、有防衰减治理**的流水线。

### 经验库的数据结构

经验库就是一个纯本地 JSON 文件，约定放在项目根的 `qa/playbook.json`（用 `playbook.py init` 创建）。每条经验记五样东西：

| 字段 | 记什么 | 举例 |
|------|--------|------|
| `pattern` | 问题模式：什么样的缺陷 | "表格转 Markdown 时合并单元格丢内容" |
| `cause` | 根因：为什么会发生 | "按行逐格读取，没处理 rowspan" |
| `method` | 最优解：可复用的正确做法 | "改用 openpyxl 读取合并区域后重建" |
| `verify` | 怎么变成检查项 | "扫产物合并单元格数 = 原文" |
| `when` | 适用场景标签，供 P 阶段按标签筛 | `["表格", "OCR", "编码"]` |

外加三个统计字段和状态机：

```json
{
  "id": "L-003",
  "pattern": "PDCA验收清单的 command 项内嵌多行 Python 会被当字面字符致语法错",
  "cause": "JSON 字符串里的换行转义传给 python -c 时是字面反斜杠n 不是真换行，for 循环体首行报 SyntaxError",
  "method": "凡需要多行逻辑的验证，一律写成独立 .py 脚本落 qa/，command 只写『python 脚本路径 参数』",
  "verify": "command 只写脚本路径参数；脚本内用真换行、输出 scanned=N/expected=M",
  "when": ["PDCA清单command验证/含for或多行python"],
  "status": "candidate",
  "applied": 1,
  "effective": 1,
  "version": 1,
  "evidence_log": []
}
```

为什么是这五个字段、而不是随手记一段话：

- 只有 `pattern` 没有 `cause` → 换个场景就套不上，因为不知道它到底在什么条件下成立。
- 只有 `cause` 没有 `method` → 知道了问题但不知道下次该怎么做。
- 有 `method` 没有 `verify` → 无法变成机器可验的检查项，还是只能靠人记着。
- `when` 标签 → 让下次任务能**按场景精准取回**，而不是把整个库倒出来淹没清单。

`status` 是状态机：`candidate`（待验证）→ `proven`（已验证有效）→ `deprecated`（被更好方法替代或已失效，不再注入）。

`applied` / `effective` 两个计数分开记：**用了几次**和**真挡下过几次**是两件事。`evidence_log` 留存每次生效的证据原文。

### 外环的四个步骤

**① C 阶段提炼**

门禁抓出缺陷、同类全量扫描、根因确认之后，判断这个缺陷是否具有可复用性。不是所有 bug 都值得入库——一次性的环境抖动（缺字体、路径写错一层）入库只会污染经验库。可复用的才写。

```bash
python scripts/playbook.py add qa/playbook.json \
  --pattern "表格转 Markdown 时合并单元格丢内容" \
  --cause "按行逐格读取，没处理 rowspan" \
  --method "改用 openpyxl 读取合并区域后重建" \
  --verify "扫产物合并单元格数 = 原文" \
  --when 表格 --when OCR
```

五个字段缺一不可，脚本会校验。

**② P 阶段注入**

下一次同类任务开工前，先按标签取回适用经验：

```bash
python scripts/playbook.py list qa/playbook.json --when 表格
```

脚本输出每条经验的 `pattern` / `cause` / `method` / `verify`，并明确提示：**把适用的转成清单里的预防项**。转成的检查项用 `EXP-xx` 前缀标识，例如：

```json
{
  "id": "EXP-01",
  "desc": "表格转 Markdown 时合并单元格不得丢内容（来自经验库条目）",
  "verify": { "type": "command", "cmd": "python qa/check_merge_cells.py" },
  "status": "pending",
  "evidence": ""
}
```

**这一步是整个外环的价值所在**：经验不是在出事后被"记住"，而是在**计划阶段就变成了一个必过的检查项**。

**③ C 阶段验证**

某条经验确实在本轮挡住了同类问题（或用户确认方法有效），就记一次有效：

```bash
python scripts/playbook.py mark qa/playbook.json --id L-001 \
  --effective --evidence "门禁实跑输出 scanned=12/expected=12"
```

`--evidence` 是**必填**的。没证据就记有效，脚本直接拒绝：

```
[PLAY] L-001: --effective requires --evidence (gate output or user confirmation).
       No effective credit, no promotion.
```

只是"用过"但没确认有效的，记 `--applied`。

**④ 晋升与固化**

`effective >= 2` 的经验自动晋升 `proven`：

```
[PLAY] L-001 promoted to PROVEN (effective >= 2).
```

`proven` 意味着这条经验被机器验证过两次以上，是可信的默认值 —— 它是固化进默认清单模板的候选，以后所有相关任务天生带这条防护。

## 三条防衰减机制

经验库不治理必然烂掉。三个机制让它"越用越强"而不是"越用越乱"。

### 一、同一个坑再犯 = 强制升级原条目

这是最容易忽略、但最关键的一条。

朴素做法是"每次踩坑就加一条"。问题是：同一个坑踩第二次，**说明上次的方法不够好**，而不是"又发现了一个新坑"。如果照旧新增，经验库会堆满近义条目，真正有效的解法淹没在里面。

所以 `add` 时用相似度匹配（标准库 `difflib`）识别重复 pattern。命中时不新增，而是**升级原条目**：

```
[PLAY] RECURRENCE -> upgraded L-001 to v2 (status reset to candidate).
      Same defect reappearing means the previous method was insufficient; sharpen it.
```

升级动作有四个后果：

- `method` 换成新解法
- `version` +1
- `status` 打回 `candidate`（新方法还没被验证过，不能直接继承旧方法的"已验证"信用）
- `applied` / `effective` 统计**清零**（旧方法的战绩不能算到新方法头上）

`playbook.py check` 会揪出"升级过却从未验证有效"的条目：

```bash
python scripts/playbook.py check qa/playbook.json
```

超过 20 条时还会告警提示归档。**短小可读**是经验库能一直有用的前提。

### 二、无证据不许记功

经验从 `candidate` 升 `proven` 靠的是真挡下过问题，不是自我声明。

`mark --effective` 强制带 `--evidence`，没有证据就没有有效次数，晋升无从谈起。证据可以是门禁的实跑输出，也可以是用户的确认。证据原文存进 `evidence_log`，可追溯。

这一条是整个机制**不被 AI 自己糊弄过去**的关键。如果允许 AI 自己说"这条经验很有效"，那经验库很快就变成 AI 自己给自己发的表扬信。

### 三、反复修不好，本身就是最高价值的经验

内环 5 轮仍不过时，一个偷懒的做法是如实报告就结束。但这里有更值钱的信息：**为什么反复修不好**。

这通常是方法论层面的问题——比如某类任务的验收标准本身没定清楚、某类验证器天然有假失败。把它提炼成一条新经验写入库，下个任务遇到同类问题就能绕开。

**失败被转化成知识**，系统因此不会在同一类任务上反复卡死。这是 PDCA 里 A 环节真正的价值所在——A 不是"改进建议"，是"把失败变成不会再犯的机制"。

## 零 token 的实现

这一点值得单独说，因为它决定了这套机制能不能真的长期用下去。

**经验库的全部操作——写入、相似度匹配、状态机晋升、健康检查——都由本地 Python 脚本完成，运行期不调用任何大模型。**

```
playbook.py init | add | list | mark | check
```

标准库实现，不装任何第三方包。所以：

- 跑经验库**不烧 token**，可以每次开工前无脑跑一遍
- 判定是**确定性的**，不会今天说"有效"明天说"无效"
- 没有网络依赖，离线可用

大模型只做它该做的那部分：从缺陷里提炼根因和最优解、写出可执行的 `method`。**判断和记账交给脚本**——这正是这个 skill 一贯的做法，门禁也一样。

## 真实案例

下面四条来自真实项目运行，都是"门禁抓出来 → 提炼入库 → 下次被挡住"的完整链路。原始内容在仓库的 `assets/playbook.demo.json`。

### L-003 · 清单里的多行 Python 命令被当字面字符

- **现象**：门禁把一项**其实没问题的产物**判成 FAIL，命令实跑报 `SyntaxError`。
- **根因**：JSON 字符串里的换行转义传给 `python -c` 时是字面反斜杠加 n，不是真换行，`for` 循环体首行就炸了。
- **最优解**：凡需要多行逻辑的验证，一律写成独立 `.py` 脚本落 `qa/`，`command` 只写"python 脚本路径 参数"；脚本内用真换行、输出 `scanned=N/expected=M`。
- **防复发**：下轮建清单时，"command 项是否内嵌多行 Python"作为预防项在 P 阶段就被检查。

### L-002 · 链接检查正则写死结尾，误判正确链接
- **现象**：一条**完全正确**的链接被判 FAIL，是典型的假失败。
- **根因**：正则写死了"路径后紧跟闭合标记"，但合规写法允许全路径加别名（`[[目录/文件|别名]]`），带别名的正确链接被误判。
- **最优解**：正则只匹配前缀（不要求结尾闭合），或直接用 `command` 验证器按 target 前缀判定；与既有校验脚本的判据保持一致。
- **防复发**：写链接类验证器时，"判据是否覆盖带别名写法"成为预防项。

### L-004 · 噪声检查误伤正文里的合法说明

- **现象**：一份**内容正确**的文档被判"噪声残留"FAIL。
- **根因**：检查脚本禁止正文出现某个控制符，但来源说明里为了讲清楚"已经去掉了控制符"，**把该符号的字面量写了出来**——被自己的规则误伤。
- **最优解**：说明性文字用自然语言描述噪声（如"尖括号竖线包裹的语言标记"），而不是写出符号字面量；附件保留原样不受此限。
- **防复发**：写禁用词检查时，"谁会合法提到它"成为必须先想清的问题。

### L-001 · 语音识别稿的专名同音错字

- **现象**：转写稿里的人名、外文专名同音错字，被当成正确术语固化进笔记，还会被后续条目引用扩散。
- **根因**：本地语音识别在中文数字还原上准，但专名同音误识率高；不核验直接蒸馏，错误会一级级传下去。
- **最优解**：成稿前逐条纠正人名/专名；一手出处用联网核验，**查不到就写"未获取"**；错字对照表单独存放，禁把转写原样当术语依据。
- **防复发**：蒸馏类任务开工前先读错字对照表，专名核验成为清单里的必过项。

四条里有三条（L-001 / L-002 / L-003）的共同点是：**门禁判 FAIL，但产物其实是对的**。这类假失败如果不提炼成经验，AI 下一轮还会用同样的错判据继续冤枉好产物。

## 怎么用起来

### 装上就能用

```bash
# WorkBuddy Skill
git clone https://github.com/MINGHOU888/pdca-strict-delivery
copy /Y pdca-strict-delivery "%USERPROFILE%\.workbuddy\skills\"

# 或纯提示词版：把仓库根目录 全量交付PDCA.md 里 --- 之间的整段复制到你常用 AI 的每次任务开头
```

### 三条命令

```bash
# 开工前：按本任务标签取回适用经验，转成清单里的预防项
python scripts/playbook.py list qa/playbook.json --when 表格

# 做完复盘：把可复用的坑写进经验库（五个字段填全）
python scripts/playbook.py add qa/playbook.json \
  --pattern "..." --cause "..." --method "..." --verify "..." --when 表格

# 交付前：检查经验库健康度
python scripts/playbook.py check qa/playbook.json
```

### 依赖关系

```
经验库(qa/playbook.json)
        ↑ P 阶段加载                    ↓ A 阶段沉淀
     清单(EXP-xx 预防项)  ──门禁通过──→  缺陷根因
        ↑                                    ↓
        └── 下次同类任务在计划阶段就被挡住 ──┘
```

### 没有脚本环境怎么办

不用任何工具的降级版也保留同样机制，只是载体从 JSON 换成一份 Markdown 清单（`教训清单.md`），每条压到三段：**触发信号 / 正确做法 / 验证方式**。

规则一样：

- 每次开工先读一遍，用得上的变成清单里的"预防项"
- 发现可复用错误，修好后附上触发方式再入库
- 同一错误第二次出现，**改写升级原条目**并标注重犯，不新增重复条目
- 一条方法累计两次"有效"才标记"已验证"，以实际证据或用户确认为准
- 清单超过 20 条时合并同类、归档旧条目

机制相同，只是靠自律而非脚本。

---

## 一句话总结

**内环用门禁保证这一次做对，外环用经验库保证下一次做得更快。**

外环之所以不是"把教训存起来"，靠三件事：P 阶段就把经验变成立即必过的检查项；同一个坑再犯强制升级而非新增；没证据不许记功。

外加一条：**修不好本身也是经验**——失败被转化成知识，系统才真的不会在同类任务上反复卡死。
